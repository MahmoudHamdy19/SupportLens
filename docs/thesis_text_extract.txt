Chapter 1

Introduction

1.1 Motivation, Problem, and Research Gap

Open-source software (OSS) has become a foundational component of modern software
systems. Package registries such as PyPI for Python distribute hundreds of thousands of reusable
libraries, and applications routinely depend on dozens of packages, directly or transitively. This
dependency structure delivers substantial efficiency gains but also introduces systemic risk: a
vulnerability in a widely used package can propagate to every application that depends on it. Li
and Paxson conducted a large-scale empirical study of security patches and found that security
issues reside in code bases for years, with nearly 5% of security patches negatively impacting the
software and over 7% being incomplete [1]. Alfadel et al. [2] similarly observed that Python
packages commonly exhibit prolonged vulnerability disclosure and fixing delays, with a significant
percentage of affected PyPI packages remaining unfixed after public disclosure. Liu et al. [3]
further demonstrated that a large portion of CVEs are publicly discussed before a patch is
available, exposing vulnerabilities to potential exploitation. These findings underscore a critical
practical question for software adopters: which versions of a given package are actually receiving
security fixes?
To address this question, many open-source projects publish a security policy in a SECURITY.md
file, as recommended by GitHub [4]. These policies typically describe how to report vulnerabilities
and often declare which versions of the project remain supported with security updates. Such a
declaration is, in effect, a commitment to users: "if you run a version in this range, we will fix
security issues in it." However, a published commitment is not equivalent to a verified one. The
policy states what the maintainers intend; the actual behavior is observable only through the
project's vulnerability advisories, release history, and fix records.
Choetkiertikul et al. [5] recently analyzed the security policies of 679 PyPI packages hosted on
GitHub and characterized their content, adoption, and relationship to project-level security
practices [5]. Their study identified eight distinct content categories, including "Scope of Practice,"
which captures version-support statements. However, the study examined the presence and
structure of these statements, not whether they are consistent with the project's published
Chapter 1. Introduction  2

vulnerability and fix evidence. The authors explicitly recommended future work on automated
methods that detect practices inconsistent with declared policies, and on linking policy analysis
with longitudinal vulnerability data.
This thesis addresses that gap. We focus on a specific, measurable commitment contained in
many security policies: the declaration of which versions receive security fixes. We investigate
whether this declared commitment can be automatically extracted from SECURITY.md using
Artificial Intelligence, and whether it is consistent with publicly available evidence drawn from
vulnerability databases such as OSV [6], release metadata from PyPI [7], and advisory records
from GitHub [4]. The task is inherently difficult because commitments are expressed in natural
language, are not standardized, and often rely on relative terms such as "latest release" whose
meaning depends on a temporal reference. Furthermore, the evidence required to assess
consistency is heterogeneous, temporally distributed, and sometimes incomplete. Distinguishing
genuine inconsistency from insufficient evidence is therefore a central design requirement, not
an afterthought.
To articulate this gap precisely, we decompose it into three interrelated dimensions that directly
motivate our proposed solution:
First, the Characterization Gap (X): Existing approaches successfully characterize policy content
and measure their adoption across ecosystems, but they treat security policies merely as
documents to be described, rather than as measurable commitments to be verified.
Second, the Verification Gap (Y): There is currently no automated approach to verify the
consistency between declared version-support commitments and the actual vulnerability and fix
evidence published for a project.
Third, the Evidence Complexity Gap (Z): The evidence required to perform such verification is
heterogeneous and temporally distributed across multiple sources (e.g., OSV, PyPI, GitHub).
Existing tools do not address the challenge of aligning these multi-source records with a specific
point in time.
Consequently, it remains unclear whether declared version-support commitments can be
automatically extracted, normalized, and assessed against such complex evidence in a way that is
both accurate and explainable. These three dimensionsâ€”(X), (Y), and (Z)â€”form the foundation
of the SupportLens framework introduced in Chapter 3.

1.2 Research Questions, Objectives, and Scope

 To address the identified research gap dimensions (X, Y, and Z), this thesis proposes the design,
implementation, and evaluation of SupportLens, a hybrid, explainable AI framework. The primary
objective is to automate the extraction of version-support commitments from free-form
SECURITY.md files using a fine-tuned Large Language Model, and to verify their consistency
against multi-source vulnerability and release evidence (such as OSV and PyPI). By combining AI-
based understanding with a deterministic rule engine, the framework aims to produce an
auditable verdict and a grounded explanation for each package. To systematically achieve and
evaluate this overarching goal, this research is guided by the following questions:

          Q1. How accurately can an AI-based extraction system identify and structure version-
         support commitments from free-form SECURITY.md files, compared with rule-based
         baselines?
          Q2. How effectively can the proposed framework assess the consistency between
         extracted commitments and published vulnerability and release evidence, across the five
         predefined outcome categories (Consistent, Partially Consistent, Potential Inconsistency,
         Insufficient Evidence, Unmeasurable Commitment)?
          Q3. How does the framework's performance vary across different project characteristics
         (e.g., project age, popularity, policy complexity), and what classes of cases predominantly
         produce failure or insufficient-evidence outcomes?
 The corresponding objectives are:
    1. Design and implement an AI Extraction Layer capable of identifying version-support
         commitments from free-form security policies and normalizing them into structured,
         comparable representations.
    2. Build an Evidence Integration Layer that aggregates and normalizes data from PyPI, OSV,
         and GitHub Advisory, linking each package to its repository, vulnerability records, and
         release timeline.
    3. Design and implement an explainable Rule-Based Assessment Layer that evaluates the
         aligned evidence to produce one of five distinct outcomesâ€”namely, Consistent, Partially
         Consistent, Potential Inconsistency, Insufficient Evidence, and Unmeasurable
         Commitmentâ€”together with a grounded justification for each verdict.
    4. Evaluate the framework against a manually annotated dataset using precision, recall, and
         F1-score. Furthermore, collect and analyze a structured human evaluation from domain
Chapter 1. Introduction  4

         experts to assess the correctness, completeness, and traceability of the generated
         explanations.
    5. Conduct an error and robustness analysis across different project characteristics (e.g.,
         project age, popularity) to identify the limitations and failure modes of the automated
         approach.
 Scope and assumptions. The study is restricted to PyPI packages whose GitHub repository and
SECURITY.md file can be identified, and whose security policy contains a version-support
statement. Only publicly available evidence is used. The framework does not claim to cover non-
version-related security commitments, does not evaluate private or undisclosed fixes, and does
not assess projects outside the PyPI/GitHub ecosystem. These boundaries are intentional and are
revisited in the limitations discussion in Chapter 5.

1.3 Contributions

 This research makes the following contributions to the fields of software security and applied
 artificial intelligence:

    1. Methodological Contribution: A novel, explainable five-layer architectural framework
         (SupportLens) for automated security policy verification. This architectureâ€”comprising
         Data Acquisition, AI Extraction, Evidence Integration, Rule-Based Assessment, and
         Explanation Generationâ€”uniquely bridges the gap between the generalization required
         to understand natural-language policies and the strict auditability required for security
         assessments.

    2. Extraction Contribution: An AI-based extraction model specifically designed to transform
         unstructured SECURITY.md text into structured, measurable version-support
         commitments. This is accompanied by a newly created, manually annotated dataset
         (serving as a ground truth) and a systematic performance comparison against rule-based
         and zero-shot baselines.

    3. Consistency-Assessment Contribution: A novel, temporally aware rule-based assessment
         engine that evaluates declared commitments against multi-source vulnerability evidence.
         It introduces a five-category taxonomy (including Insufficient Evidence) to prevent
         conflating missing data with actual security inconsistencies.

    4. Empirical Contribution: An empirical evaluation demonstrating the framework's
         effectiveness on a curated set of PyPI packages. This includes quantified findings on
         extraction accuracy, verdict accuracy, and a comprehensive analysis of failure modes in
         automated policy verification.

    5. Artifact Contribution: A reproducible, open-source implementation and the manually
         annotated dataset, which will be made publicly available to support future research and
         tooling in security policy compliance.

Chapter 2

Background and Related Work

2.1 Background and Foundations

 This section introduces the theoretical and technical concepts required to understand the
SupportLens framework. It defines the terminology used throughout the thesis and explains
the foundational mechanisms of security policies, vulnerability data, and explainable AI.

 2.1.1 Open-Source Security Policies
 In modern software engineering, a security policy defines the procedures, expectations, and
commitments that open-source maintainers publish for users and contributors. On platforms
like GitHub, this policy is conventionally stored in a SECURITY.md file located in the
repository root, the docs/ folder, or the .github/ folder [4]. GitHub recommends that this file
include, at a minimum, a method for reporting vulnerabilities and a description of the
versions that remain supported with security updates.
 Kanaji et al. [9] analyzed 711 issues related to SECURITY.md and found that 79.5% were
requests to add the file, indicating that adoption is still in its early stages [8]. Ayala et al.
studied 2,581 projects and found that only 52.7% had a vulnerability reporting policy. While
policies are increasingly recognized as important, their content remains heterogeneous,
unstructured, and often incomplete.
 Definition (Version-Support Commitment). In this thesis, a version-support commitment is
a statement within a security policy that specifies which versions of the project receive
security fixes. Such commitments may be expressed as explicit version ranges (e.g., 5.1.x, >=
3.9), as relative descriptions (e.g., "the most recent release"), or as a combination of both. A
commitment is measurable if it can be mapped to a concrete set of version identifiers within
a defined temporal reference; otherwise, it is unmeasurable.

2.1.2 Vulnerability and Release Data

To verify a security commitment, three public sources provide the necessary empirical

evidence:

ï‚· OSV (Open-Source Vulnerabilities): Provides a machine-readable schema

describing vulnerabilities, affected version ranges, and fix information [6].

ï‚· PyPI JSON API: Provides package metadata and a complete release timeline, enabling

the reconstruction of which versions existed at a given time [7].

ï‚· GitHub Advisory Database: Provides curated security advisories linked to CVE

identifiers, often including fixed version information [4].

Li and Paxson [10] demonstrated the feasibility of merging vulnerability metadata with

source code repositories to study patch development lifecycles. Their methodologyâ€”

extracting Common Vulnerabilities and Exposures (CVE) entries, scraping external

references, and linking them to Git commitsâ€”provides a foundational template for evidence

integration. Bao et al. further refined the identification of affected version ranges through the

V-SZZ algorithm, which uses line mapping to trace back to the earliest inducing commit.

However, Jiang et al. [11] analyzed the data inconsistency of open-source vulnerability

repositories and found significant discrepancies in how released versions are translated into

Common Platform Enumeration (CPE) metadata, leading to false positives or missed alerts in

automated scanners.

2.1.3 Natural Language Processing for Policy Text

Extracting structured information from security policies is a natural language

understanding problem. Relevant techniques include Named Entity Recognition (NER) for

identifying version tokens and Relation Extraction (RE) for linking tokens to support or non-

support predicates.

Dagdelen et al. [12] demonstrated that fine-tuned large language models (LLMs) can extract

structured knowledge from scientific text by outputting JSON documents according to a

predefined schema. Their approach, termed LLM-NERRE, achieves strong performance with

only a few hundred annotated examples, showing that joint NER and RE can be performed

without enumerating all possible n-ary relations. Similarly, Petrillo et al. [13] applied

transformer models to the classification of security requirements, achieving an F1-score of

0.90 and introducing explainability through attention visualization heatmaps.

Conversely, rule-based extraction using regular expressions is effective for explicit patterns

such as 5.x or >=3.9, but is brittle to paraphrases, negation, and implicit references, which are

common in security policies. Pinckney et al. [14] analyzed over a million packages in the NPM

ecosystem and showed that semantic versioning policies significantly impact the security
Chapter 2. Background and Related Work  8

posture of downstream dependents, highlighting the complexity of version range semantics
and the need for precise normalization.

 2.1.4 Explainable AI and Hybrid Systems
 Explainability is a major requirement of this research. A purely generative approach cannot
guarantee auditability, traceability, or the absence of hallucination. Therefore, this research
adopts a hybrid framework where AI is used for understanding (extracting the policy claim),
and deterministic rules are used for judgment (producing the final verdict).
 Lundberg and Lee [15] introduced SHAP (SHapley Additive exPlanations), a unified
approach for interpreting model predictions based on cooperative game theory. Yi et al. [16]
developed IVDetect, which uses Program Dependency Graphs (PDG) to provide fine-grained
interpretations of vulnerability detection by identifying crucial sub-graphs. These works
demonstrate that explainability can be achieved without sacrificing performance, provided
that the explanation is grounded in observable evidence. Transformer architecture [17] and
its bidirectional variant, BERT [18], provide the foundational mechanisms for the language
models used in this thesis, while Cohen's Kappa [19] and the Mann-Whitney U test [20]
provide the statistical rigor for evaluation.

2.2 Related Work

 This section reviews the literature thematically, focusing on how prior work has addressed
security policies, vulnerability disclosure, and automated compliance.

 2.2.1 Empirical Studies of Security Policies
 Alfadel et al. [2] conducted a large-scale empirical analysis of the Python ecosystem. By
mining vulnerability databases and linking them to package repositories, they analyzed 1,396
vulnerability reports across 698 packages. Their methodology revealed prolonged delays in
vulnerability disclosure and fixing, providing the empirical motivation for verifying version-
support commitments.
 Ayala et al. [9] examined the adoption of security workflows and policies in popular GitHub
repositories. By mining data from 8,073 projects with disclosed vulnerabilities, they
compared the disclosure practices of projects with and without security policies. They
observed that projects with security policies exhibited more coordinated disclosure practices
(63.8% following a Coordinated Vulnerability Disclosure (CVD)-like process) compared to
those without policies (49.7%).
Chapter 2. Background and Related Work                                          9

Zahan et al. [22] introduced the OpenSSF Scorecard, which includes a Security-Policy check

that evaluates the presence and sufficiency of a SECURITY.md file. Their methodology

involved running this automated tool across nearly a million npm and 211,088 PyPI

packages. The results found that only 3.2% of npm and 2.5% of PyPI packages had a

SECURITY.md file. While the Scorecard assesses the presence of the file, it does not verify the

consistency between declared commitments and observed evidence.

Liu et al. [3] conducted a large-scale empirical study of vulnerability disclosure management.

Their methodology combined the analysis of 21,501 Common Vulnerabilities and Exposures

(CVEs) from the National Vulnerability Database (NVD) and GitHub Advisory with a survey

of 770 practitioners. By comparing actual disclosure timelines with developer preferences,

they found that while over 80% support CVD, only 56% of vulnerabilities conform to it in

practice, highlighting the gap between declared practices and actual behavior.

 2.2.2 Content Analysis of SECURITY.md
 Choetkiertikul et al. [5] analyzed 679 PyPI projects and characterized the content of 303
security policies. Their study identified eight categories of content, including "Scope of
Practice," which captures version-support statements. They examined reporting mechanisms
and their alignment with developer practice and analyzed correlations between policy
content and project characteristics.
 However, their analysis of version-support statements is descriptive: they identify the
category but do not verify whether the declared version support is consistent with the
vulnerability and fix evidence. The authors explicitly recommend automated methods for
detecting non-compliant practices and for integrating policy analysis with longitudinal
vulnerability data. This thesis directly addresses that recommendation.

 2.2.3 Vulnerability Disclosure and Management
 Kanaji et al. [8] investigated the challenges developers face regarding SECURITY.md
adoption. By manually classifying a sample of 711 issues related to the file, they found that
issues containing links to documentation were closed two days faster than those without
links. This suggests that providing concrete guidance facilitates the adoption and
implementation of security policies.
 Ayala et al. [9] investigated vulnerability disclosures by analyzing a dataset of 3,798
reviewed GitHub security advisories and 4,033 disclosed bug bounty reports. As part of their
analysis, they found that 61% of the top 100 repositories using dompdf [25] (a popular PHP
library for HTML to PDF conversion) were vulnerable to a critical CVE (Common
Vulnerabilities and Exposures) that was absent from the National Vulnerability Database
Chapter 2. Background and Related Work  10

(NVD). This highlights critical gaps in the vulnerability disclosure and alerting process for
downstream dependents.
 Assal and Chiasson [23] conducted a qualitative interview study with 13 developers to
explore real-life software security practices. Their inductive analysis revealed significant
deviations from best practices, often driven by factors such as division of labour, security
knowledge, and company culture. Their work provides important context for understanding
why security policies may not be fully implemented in practice, emphasizing the human and
organizational factors behind policy compliance.

 2.2.4 Automated Compliance and Consistency Checking
 Extending compliance checking to free-form security policies requires an extraction stage
that transforms text into structured claims, followed by a verification stage. Thirumalaisamy
[24] proposed an AI-assisted framework for verifying SBOM (Software Bill of Materials)
accuracy and detecting "drift" â€” discrepancies between a declared SBOM and actual build
artifacts. The framework assigns a severity score to discrepancies and can block
deployments. Their work demonstrates the feasibility of automated consistency checking,
albeit for structured SBOM data rather than natural-language policies.
 Jiang et al. [11] evaluated the data inconsistency of open-source vulnerability repositories,
revealing that discrepancies in release version translation often lead to false positives in
automated scanners, underscoring the need for robust evidence integration and
normalization.

 2.2.5 Information Extraction from Software Artifacts
 Transformer-based models have been successfully applied to extracting structured
information from software documentation and bug reports. Petrillo et al. [13] demonstrated
that fine-tuned transformers can classify security requirements with an F1-score of 0.90,
providing interpretable explanations via attention visualization . Dagdelen et al. [12] showed
that LLMs fine-tuned on a few hundred examples can extract complex hierarchical
relationships, outputting structured JSON documents according to a predefined schema.
These properties are directly relevant to the extraction of version-support commitments,
which may involve multiple version ranges, exceptions, and temporal references.
 To synthesize the reviewed literature, Table 2.1 provides a comparative summary of the
representative related approaches discussed in this chapter. The table categorizes each work
based on its primary functionality, the AI model utilized (if any), its reported strengths, and

2.3 Synthesis and Research Gap

 The literature reviewed in this chapter establishes that security policies in open-source
projects have become a recognized object of empirical study. Prior work has characterized
their content, measured their adoption, and correlated their presence with project-level
security practices. However, three specific dimensions remain unaddressed, and together
they define the research gap that this thesis aims to close.

 First, existing approaches achieve policy characterization and adoption measurement (X).
Studies such as Choetkiertikul et al. [5], Kanaji et al. [8], and Zahan et al. [22] classify the
content of security policies, measure adoption rates, and assess whether policies include
sufficient information for reporting. However, these works treat the policy as a document to
be described, not as a set of commitments to be verified.
Chapter 2. Background and Related Work  14

 Second, existing approaches do not verify the consistency between declared version
support and published vulnerability and fix evidence (Y). While Li and Paxson [1] and Bao et
al. [10] established methodologies for linking vulnerabilities to code changes and version
ranges, and while Liu et al. [3] and Ayala et al. [9] documented gaps between declared and
actual disclosure practices, no prior work has systematically compared what a project claims
about version support with what its vulnerability records show. The closest work,
Choetkiertikul et al. [5], identifies the "Scope of Practice" category but stops short of assessing
whether the declared scope aligns with published evidence.

 Third, the evidence required to assess this consistency is heterogeneous, temporally
distributed, and sometimes incomplete (Z). A version-support commitment is meaningful
only relative to a temporal reference: the phrase "we support the latest release" means
different things at different points in time. Verifying such a commitment requires aligning
policy text with vulnerability publication dates, release timelines, and fix records drawn from
multiple sources (OSV, NVD, GitHub Advisory, PyPI). This temporal and multi-source
complexity has not been addressed by prior work on policy analysis.

 2.3.1 From Research Gap to Methodology
 To address the identified research gaps, this thesis proposes SupportLens, a hybrid,
explainable five-tier architecture that operationalizes the solution. To prevent confusion with
neural network layers, we refer to the architectural components as "Tiers". The architecture
maps directly to the three gap dimensions defined in Section 1.1:

    ï‚· (X) The Characterization Gap: The lack of structured, verifiable policy claims. To
         address this, Tier 0 (Data Acquisition) retrieves the raw security policy, and Tier 1 (AI
         Extraction) transforms the unstructured text into structured, measurable
         commitments rather than descriptive text.

    ï‚· (Z) The Evidence Complexity Gap: The challenge of heterogeneous and temporally
         distributed evidence. To address this, Tier 2 (Evidence Integration) normalizes and
         aligns multi-source data (from OSV, PyPI, and GitHub Advisory) using explicit
         temporal resolution.

    ï‚· (Y) The Verification Gap: The absence of automated consistency assessment. To
         address this, Tier 3 (Rule-Based Assessment) uses a deterministic rule engine to
         compare the declared commitments with the aligned evidence, producing a five-
         category verdict.
Chapter 2. Background and Related Work                                                  15

ï‚· The Explainability Requirement: Finally, to ensure the system is auditable, Tier 4

(Explanation Generation) produces an evidence-grounded justification for every

verdict, linking each output directly to the underlying sources.

The full details of this architecture, including its problem formulation, implementation, and

evaluation protocol, are presented in Chapter 3.

 3.1.1 Research Paradigm and Strategy
 This thesis follows a Design Science Research (DSR) paradigm. The primary contribution is the
design, implementation, and evaluation of the frameworkâ€”SupportLens. The research
addresses a concrete problem in open-source software security governance (the gap between
declared and observed version support) and produces a system that explains its own reasoning.
 The methodology integrates three distinct technical traditions:

    1. Software Security: Mining software repositories and vulnerability databases (e.g., OSV,
         NVD) to extract empirical evidence regarding vulnerability disclosure, affected versions,
         and release histories.

    2. Natural Language Processing (NLP): Schema-constrained information extraction from
         technical documentation (specifically SECURITY.md files).

    3. Explainable AI (XAI): A hybrid design combining learned neural components (for
         understanding) with deterministic symbolic reasoning (for auditable judgment).

3.3 Experimental Design and Evaluation

 This section defines the experimental setup required to answer the research questions (Q1, Q2,
and Q3).
 3.3.1 Datasets and Gold Standard
 Since no existing benchmark dataset provides labels for version-support commitments in
SECURITY.md files, this thesis will construct a new manually annotated reference dataset to
serve as the ground truth for evaluation.

    ï‚· Data Collection: A Python script queries the PyPI JSON API to retrieve packages that have
         a valid GitHub repository link and an accessible SECURITY.md file. Only packages
         containing a version-support statement will be retained.

    ï‚· Manual Annotation Process: A stratified random sample of 300 policies will be
         annotated. The annotation will be performed independently by two annotators: (1) the
         primary author of this thesis, and (2) an independent peer researcher with a background
         in computer science. To ensure consistency, both annotators will use a predefined
         Annotation Guideline (Codebook) and a graphical annotation tool (e.g., Label Studio).
         They will label the commitment tuple c=âŸ¨t,Ï„,v,TâŸ© and the expected verdict y.

    ï‚· Adjudication: In cases of disagreement between the two annotators, a third party (the
         thesis supervisor) will act as an adjudicator to resolve the conflict and establish the final
         ground truth label.

    ï‚· Inter-rater Reliability: Before adjudication, the level of agreement between the two
         annotators will be measured using Cohenâ€™s Kappa [19] to ensure the annotations are
         objective and reliable (target Îºâ‰¥0.80).

    ï‚· Data Splits: Once the reference dataset is finalized, it will be partitioned into 70%
         training (for fine-tuning the Tier 1 extraction model), 15% validation, and 15% test sets.

 3.3.2 Baselines
 To rigorously evaluate the contribution of the proposed AI Extraction Tier (Tier 1), its
performance will be compared against three distinct baselines, ranging from traditional
deterministic methods to standard machine learning approaches:

    1. Rule-Based Baseline: A deterministic script utilizing Regular Expressions (Regex) and
         keyword matching. This baseline will use predefined patterns to extract explicit version
         numbers (e.g., matching patterns like \d+\.\d+\.\d+ or >= 3.9) and trigger words (e.g.,
         "latest", "supported", "end-of-life"). This represents the traditional, non-learning
Chapter 3. Methodology  25

         approach commonly used in static analysis tools. It is expected to perform well on explicit
         ranges but fail on complex or implicit natural language phrasings.
    2. Zero-Shot LLM Baseline: The base Qwen2.5-7B-Instruct model [26] without any fine-
         tuning. The model will be prompted directly using In-Context Learning (ICL) with the
         same JSON schema instructions provided to the fine-tuned model. This baseline measures
         the model's inherent pre-trained capability to understand policy text and format it
         correctly, serving as a control to isolate the exact value added by our domain-specific fine-
         tuning.
    3. Fine-Tuned RoBERTa Baseline: A traditional, encoder-only transformer model,
         RoBERTa-base [37], fine-tuned specifically for Token Classification (Named Entity
         Recognition). This model will be trained to identify the start and end tokens of the
         commitment text, the version expression, and the temporal reference. Unlike the LLM
         which generates structured JSON, RoBERTa will predict span labels.

             o Fine-Tuning Details: Because RoBERTa is a relatively small model (approx. 125M
                  parameters), it will undergo standard full-parameter fine-tuning (updating all
                  weights). We will use a Cross-Entropy loss function, the AdamW optimizer, a
                  learning rate of 2 Ã— 10âˆ’5, and a batch size of 16 over 5 epochs.

 A Note on Parameter-Efficient Fine-Tuning (LoRA): It is important to distinguish the fine-
tuning strategies. While the baseline RoBERTa model undergoes standard full fine-tuning, the
primary Qwen2.5-7B model (detailed in Section 3.2.2) utilizes LoRA (Low-Rank Adaptation)
[27]. Because Qwen has 7 billion parameters, full fine-tuning would require prohibitive GPU
memory. LoRA freezes the original weights and injects small, trainable rank decomposition
matrices into the attention layers. This allows the 7B model to learn the specific policy extraction
task efficiently (training only ~1-2% of the parameters) without catastrophic forgetting, making
the approach both computationally feasible and highly effective.

    Fixing the seeds guarantees that any researcher re-running the code will obtain the
    exact same data partitions and model behavior, eliminating randomness as a
    confounding variable.

ï‚· Hyperparameters and Hardware: Detailed hardware specifications (e.g., GPU
    model, CUDA version) and a comprehensive list of all hyperparameters (e.g., learning
    rate, batch size, LoRA rank) will be documented in Appendix C.

3.4.2 Responsible AI Considerations
   ï‚· Hallucination Mitigation: By using a deterministic rule engine for verdicts (Layer 3)
       and template-based grounding for explanations (Layer 4), the system avoids the
       generative hallucination risks common in pure LLM applications.
   ï‚· Bias: The study is limited to PyPI and GitHub, which may introduce ecosystem bias.
       This is explicitly stated as a limitation, and the framework is designed to be extensible
       to other ecosystems in future work.
   ï‚· Transparency and Human Oversight: The system is designed to be a co-pilot for
       security analysts, not a replacement. The five-category verdict ensures that
       ambiguous cases are flagged for human review rather than forced into a binary
       pass/fail.
